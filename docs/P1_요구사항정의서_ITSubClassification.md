# P1_요구사항정의서_ITSubClassification — IT 세부 분류(2차) Phase 1 데이터 준비 요구사항 정의서

1차(Phase 0~5, LR 5-class) 완료 후 진행하는 **유지보수 확장**의 첫 산출물이다. 1차
Phase별 문서가 폐기되어 물리적 충돌이 없으므로, [[Scope_Definition]] 7절 로드맵의 Phase
번호를 그대로 재사용한다 — 이 문서는 2차의 **Phase 1(데이터 준비)** 요구사항정의서다.
[[CLAUDE.md]] 3절 "작업 진행 순서"(요구사항정의서→설계서→코드/테스트→테스트결과서) 및
7절 "유지보수 단계 예외"에 따라, **1차와 공통인 불변 부분은 재서술하지 않고
[[Architecture_Design]](0절·9절)와 [[Scope_Definition]](2.2·2.3·3.4절)를 참조**한다. 이
문서는 그 중 **데이터 준비 범위(2차 학습 데이터 확보)에 한정된 변경·추가 사항만** 다룬다.
다음 산출물은 `P1_설계서_ITSubClassification.md`(설계서)에서 다룬다.

**1차 산출물(`data/<version>/role_01~09_*.jsonl`, `data.jsonl`, `train/test/val.jsonl`,
1차 코드·모델·API 계약)은 이 문서의 범위에 포함되지 않으며 어떤 방식으로도 수정하지
않는다** — [[Scope_Definition]] 8절 Golden Rule 4(1차 불변 원칙), [[Architecture_Design]]
9.1절.

## 1. 목적 (Why)

Phase 3(2차 모델 학습)·Phase 4(2차 검증)에 투입할 `it_sub_train.jsonl`/
`it_sub_test.jsonl`/`it_sub_val.jsonl`을 만든다([[Architecture_Design]] 9.3절 데이터
흐름의 `A2`→`C2` 구간). 1차가 `IT`로 판정한 쿼리에 대해서만 동작하는 세부 분류기
(`DBA`/`DEVOPS`/`OS`/`NETWORK`/`MIDDLEWARE`, 5종 멀티라벨)의 학습 데이터이며, 이
데이터의 라벨 품질(특히 복합 라벨의 정확성)이 2차 파이프라인 전체의 신뢰도를 좌우한다.
(당초 6번째 라벨로 검토했던 `ETC`는 학습 라벨에서 제외 — [[Scope_Definition]] 2.2절
v2.1, 2절 참고.)

## 2. 배경 및 제약

- 1차 IT 데이터(`data/v0.2/role_01~05_*.jsonl`, 역할당 40건, 총 200건)는 5개 IT 직무
  역할(미들웨어/OS/네트워크/DBA/DevOps) 프롬프트로 생성되어 각 레코드가 **주로 하나의
  역할**을 대표하지만, 2차는 멀티라벨 전제이므로 "역할=유일한 정답 라벨"로 그대로
  재사용할 수 없다([[Scope_Definition]] 2.2절). 각 레코드를 재검토해 추가로 해당하는
  라벨이 있는지 확인·부여하는 **재라벨링**이 필요하다.
- **`ETC`는 학습 라벨이 아니다(v2.1)**: 5개 라벨 확률이 모두 threshold 미만이면 파생
  "미분류" 상태로 처리하므로, ETC 전용 데이터를 수집하지 않는다([[Scope_Definition]]
  2.2절). 이 문서의 데이터 확보 범위는 5개 라벨에만 한정된다.
- 역할 간 경계에 걸친 **복합 라벨** 질의(예: DBA+MIDDLEWARE, OS+NETWORK)는 단일 라벨
  데이터만으로는 학습될 수 없는 패턴이므로, 의도적으로 신규 생성해야 한다
  ([[Scope_Definition]] 3.4절 ②).
- 1차 `dataset.split`(클래스당 단순 stratified 3:1:1)은 레코드당 라벨 1개라는 전제로
  설계되어 있어, 레코드가 여러 라벨에 동시에 속하는 2차 데이터에는 그대로 쓸 수 없다 —
  라벨별 최소 개수를 보장하는 **반복 계층화(iterative stratification)** 방식의 별도
  분할 로직이 필요하다([[Scope_Definition]] 3.4절, [[Architecture_Design]] 9.2절
  `it_sub_classification/dataset/split.py`).
- 원본 로딩·저장은 기존 `DataRepository`/`JsonlRepository` 추상화를 코드 무수정으로
  재사용한다([[Architecture_Design]] 9.2절, [[Scope_Definition]] 2.3절 검토 결과).

## 4. 기능 요구사항

### 4.1 입력 스키마

**① 재라벨링 대상**(기존, 1차 산출물 — 읽기 전용 입력)

`data/v0.2/role_01_middleware.jsonl` ~ `role_05_devops.jsonl`(1차와 동일 스키마: `질의`/
`응답`/`카테고리`). 역할 번호 → 2차 라벨 1차 대응: `01`→`MIDDLEWARE`, `02`→`OS`,
`03`→`NETWORK`, `04`→`DBA`, `05`→`DEVOPS`.

**② 신규 생성 콘텐츠**(신규, 코드 밖에서 확보 — 입력)

1차 `role_*.csv`/`role_*.jsonl`과 동일한 원시 스키마(`질의`/`응답`/`카테고리`="IT")로
확보되며, 단일 라벨분과 복합 라벨분을 구분할 수 있는 형태로 전달된다(정확한 원본 파일
명명은 `P1_설계서_ITSubClassification.md`에서 확정 — 예: `role_11_composite.*`).

### 4.2 출력 스키마(`it_sub_*.jsonl`)

1차 스키마에 `세부카테고리` 필드를 추가한다.

| 키 | 타입 | 허용값 |
|---|---|---|
| `질의` | string | 1차와 동일 기준 |
| `응답` | string | 1차와 동일 기준 |
| `카테고리` | string (enum) | `IT` 고정 (2차 대상은 항상 IT) |
| `세부카테고리` | array\<string\> | `DBA`/`DEVOPS`/`OS`/`NETWORK`/`MIDDLEWARE` 중 **1개 이상**, 중복 원소 금지 |

예:
```json
{"질의": "톰캣 커넥션 풀이 자꾸 끊기는데 DB 락 때문인지 WAS 설정 때문인지 모르겠어",
 "응답": "...", "카테고리": "IT", "세부카테고리": ["MIDDLEWARE", "DBA"]}
```

### 4.3 재라벨링

- 대상: `role_01~05_*.jsonl` 총 200건 전량.
- 각 레코드에 대해 (a) 역할 대응 라벨(주 라벨)은 항상 포함, (b) 응답 내용을 재검토하여
  추가로 해당하는 라벨이 있으면 `세부카테고리` 리스트에 추가한다.
- 재라벨링 판단 근거(어떤 레코드를 왜 복수 라벨로 보강했는지)를 검토서로 남긴다.

### 4.4 신규 데이터 통합

- 신규 단일 라벨 데이터(라벨당 목표 보유량 확보용)와 신규 복합 라벨 데이터를
  각각 4.2 스키마로 변환한 뒤, 재라벨링된 200건과 함께 `it_sub_data.jsonl`로 재조합한다.
- 목표 양성(positive) 건수: 라벨당 200건 이상(단일+복합 합산), [[Scope_Definition]]
  3.4절 표 기준. 총 고유 레코드 수는 라벨 중복 기여로 인해 1,000건보다 적을 수 있다.
- 전체 레코드 중 약 20~30%가 라벨 2개 이상(복합 라벨)을 갖도록 한다.
- **라벨 조합별 최소 건수(신규)**: 라벨당 개별 건수(위 목표)만으로는 부족하다 — 멀티라벨
  MLP가 실제로 학습해야 하는 것은 각 라벨의 주변 확률이 아니라 **라벨 조합의 동시 경계**이므로,
  [[Scope_Definition]] 3.4절이 의도한 5개 라벨의 `C(5,2)=10`개 실무 빈발 조합(예:
  `DBA`+`MIDDLEWARE`, `OS`+`NETWORK`, `DEVOPS`+`OS`, `NETWORK`+`MIDDLEWARE` 등)은 조합당
  **최소 30~50건**을 목표로 한다. 이 최소치를 만족하지 못하는 조합이 있으면 해당 조합만
  추가 생성한다(4.5절 참고 — Phase 4 평가 결과에 따른 반복 보강 절차와 연계).

### 4.5 데이터 규모의 반복 보강 절차(신규)

- 라벨/조합별 정확한 필요 건수는 사전에 확정하기 어렵다 — 실제로 필요한 만큼은 임베딩
  공간에서의 클래스 분리도에 달려 있고, 이는 데이터를 만들어 학습·평가해보기 전에는
  알 수 없다. 따라서 4.4절의 목표치(라벨당 200건, 조합당 30~50건, 복합 비율 20~30%)는
  **최초 생성 목표**로 삼되, 총량을 한 번에 크게 늘리는 대신 다음 반복 절차를 따른다.
  1. 최초 목표치로 `it_sub_data.jsonl`을 만들고 Phase 3(2차 MLP 학습)·Phase 4(2차 검증)를
     1회 실행한다.
  2. Phase 4의 라벨/조합별 Precision·Recall([[Scope_Definition]] 4.6절 평가 지표)을
     검토해, 유독 낮은 라벨 또는 라벨 조합이 있는지 확인한다.
  3. 부족한 라벨/조합만 추가 생성하여 `it_sub_data.jsonl`을 갱신하고 재분할·재학습·재평가한다
     (전체 재생성이 아니라 부족분만 증분).
- 이 반복은 [[CLAUDE.md]] 5절 "workflow 친화 구성" 원칙과 같은 방식으로, 각 반복 결과는
  `it_sub_data.jsonl`을 덮어쓰지 않고 버전을 구분해 남긴다(예: `it_sub_data_v2.jsonl`).

### 4.6 반복 계층화 분할

- `it_sub_data.jsonl` → `it_sub_train.jsonl`/`it_sub_test.jsonl`/`it_sub_val.jsonl`,
  비율은 1차와 동일하게 3:1:1.
- 라벨별로 각 split에 최소 보유량이 확보되도록(단순 랜덤 분할 시 희소 라벨 조합이 특정
  split에 편중될 위험 방지) 반복 계층화 방식을 적용한다. 구체 알고리즘은
  `P1_설계서_ITSubClassification.md`에서 확정한다.
- 분할은 랜덤이되 **시드 고정**(1차와 동일 원칙)으로 재실행 시 동일 결과를 보장한다.

## 8. 리스크 및 참고사항

- 재라벨링은 사람/LLM의 주관적 판단이 개입하는 작업이라 라벨러 간 기준 편차 위험이
  있다 — 검토서에 판단 기준(어떤 조건이면 복수 라벨로 보강하는지)을 명시적으로 기록해
  재현 가능성을 높인다.
- 복합 라벨 데이터 비율(20~30%)과 라벨/조합별 최소 건수(4.4절)는 사전에 정확히 산정할 수
  없는 **잠정 목표치**다 — 실제로 필요한 양은 임베딩 공간에서의 클래스 분리도에 달려
  있어 학습·평가 전에는 알 수 없으므로, 최초 목표치로 1회 생성·학습·평가한 뒤 부족한
  라벨/조합만 증분 보강하는 반복 절차(4.5절)를 기본 접근으로 한다 — 총량을 한 번에
  과도하게 늘리는 대신 평가 결과 기반으로 필요한 곳에만 투자한다.
- 반복 계층화 분할 알고리즘의 구체 구현(예: scikit-multilearn `iterative_train_test_split`
  사용 여부 등 라이브러리 의존성 포함)은 이 문서에서 확정하지 않고
  `P1_설계서_ITSubClassification.md`에서 다룬다.
- 1차 데이터는 이 작업으로 인해 어떤 경로로도 수정되지 않는다 — 7절 완료 기준의 마지막
  항목으로 명시적으로 검증한다.
