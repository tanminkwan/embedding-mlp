# P1_검토서_ITSubRelabeling — 기존 IT role 데이터(200건) 재라벨링 검토서

[[CLAUDE.md]] 7절 DocType `검토서`(정규 4단계 밖에서 발생하는 점검 문서). `P1_요구사항정의서_ITSubClassification.md`
§3 In Scope #1·#2, §4.3(재라벨링)의 산출물이다. `data/v0.2/role_01_middleware.jsonl`~
`role_05_devops.jsonl`(역할당 40건, 총 200건, **1차 산출물 — 읽기 전용, 무수정**)을
2차 멀티라벨 관점에서 재검토한 결과를 담는다.

## 1. 배경

1차 IT 데이터는 5개 역할(미들웨어/OS/네트워크/DBA/DevOps) 프롬프트로 생성되어 각
레코드가 "역할 하나 = 정답 라벨 하나"라는 전제로 만들어졌다. 그러나 2차는 멀티라벨
전제([[Scope_Definition]] 2.2절)이므로, 역할 번호를 그대로 주 라벨로 재사용하되
([[Scope_Definition]] 3.4절 대응표: `01`→MIDDLEWARE, `02`→OS, `03`→NETWORK, `04`→DBA,
`05`→DEVOPS) 각 레코드의 실제 내용을 다시 읽고 **주 라벨 외에 추가로 성립하는 라벨이
있는지**를 재검토했다.

## 2. 판단 기준

다음 기준을 모두 만족해야 보조 라벨을 부여했다 — 단순 키워드 언급만으로는 부여하지
않는다.

1. 응답이 그 다른 도메인의 **구체적인 확인/조치 행위**(명령어, 설정값, 점검 절차)를
   요구한다. (예: "DB 슬로우�쿼리 로그 확인"은 DBA 행위, "방화벽/스위치 확인"은
   NETWORK 행위)
2. 그 도메인 지식 없이는 응답에 제시된 확인 순서를 실제로 수행할 수 없다(즉,
   주 도메인 지식만으로 문제 해결이 완결되지 않는다).
3. 단순히 예시나 배경 설명으로 다른 기술을 언급한 경우는 제외한다. (예: "DB 서버는
   swappiness를 낮추는 게 일반적"처럼 곁가지 팁으로만 언급된 경우는 보조 라벨 미부여)

이 기준에 따라 애매한 경우는 보수적으로(라벨을 추가하지 않는 쪽으로) 판단했다 —
멀티라벨 비율을 인위적으로 맞추기 위해 무리하게 라벨을 늘리지 않았다([[Scope_Definition]]
3.4절의 20~30% 목표는 신규 생성 데이터 전체 기준이며, 이 재라벨링만으로 그 비율을
채우려 하지 않았다).

### 3.1 role_01_middleware → 보조 라벨 8건

| 질의 | 보조 라벨 | 근거 |
|---|---|---|
| Tomcat에서 커넥션 풀 고갈됐다는 로그 나오는데 어떻게 확인해? | +DBA | "DB 슬로우쿼리 로그로 커넥션 반환 지연 여부 확인" — DB 로그 확인이 해결 절차의 핵심 단계 |
| WebtoB와 JEUS 연동에서 504 Gateway Timeout 뜨는데 뭐부터 봐야돼? | +NETWORK | "네트워크 구간(방화벽, 스위치) 확인"이 확인 순서에 포함 |
| 무중단 배포 중에 세션 끊기는 문제 어떻게 확인해? | +NETWORK | "로드밸런서 헬스체크 주기" 확인이 필수 단계 |
| 커넥션 풀에서 릭 의심되는데 어떻게 확인해? | +DBA | "DB 쪽 idle connection 개수와 비교"가 확인 절차 |
| Apache에서 too many open files 에러 나는데 원인은? | +OS | "ulimit -n", "/etc/security/limits.conf" 등 OS 레벨 설정이 해결의 핵심 |
| 세션 클러스터링 설정했는데 세션 유실되는 경우 원인은? | +NETWORK | "멀티캐스트/유니캐스트 네트워크 통신 정상 여부 확인"이 필수 단계 |
| WebtoB에서 특정 노드만 응답 없음 상태인데 확인 순서는? | +NETWORK | "네트워크 구간 점검"이 후속 확인 단계로 명시 |
| 무중단 배포 스크립트 실행했는데 헬스체크 통과 안 되는 경우 확인 순서는? | +NETWORK | "로드밸런서/L4가 바라보는 헬스체크 경로" 확인이 핵심 원인 후보 |

## 4. 결과 통합 후 라벨 분포

재라벨링 결과 200건의 라벨별 양성 건수(레코드가 여러 라벨에 속하면 각각 카운트):

| 라벨 | 주 라벨(40건 고정) | 보조 라벨로 추가 | 합계 |
|---|---|---|---|
| MIDDLEWARE | 40 | 2 (role_03에서) | 42 |
| OS | 40 | 3 (role_01×1, role_04×2) | 43 |
| NETWORK | 40 | 14 (role_01×5, role_02×3, role_04×2, role_05×4) | 54 |
| DBA | 40 | 2 (role_01에서) | 42 |
| DEVOPS | 40 | 0 | 40 |

멀티라벨 레코드는 200건 중 21건(10.5%). [[Scope_Definition]] 3.4절의 20~30% 목표는
`data/v0.4`의 신규 생성 데이터(복합 라벨 파일 10종, 350건)가 이미 충족하므로
([[Scope_Definition]] 3.4절, 실측 250/499 ≈ 50%), 이 재라벨링 결과와 합산한 전체
2차 데이터셋 기준으로는 목표를 초과 달성한다.
